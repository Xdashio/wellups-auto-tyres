## 1. Executive Summary

v0.1 establishes the complete data layer (schema, auth, RLS, seed data), the design system (Tailwind v4 tokens + UI primitives), and a production-ready project scaffold (Next.js 15 App Router, TypeScript, Cloudflare Workers via @opennextjs/cloudflare). This plan is structured as a single handoff document. Section 17 presents execution approach options for Simon to choose from.

## 3. Architecture Decisions (ADRs)

### ADR-01: Frontend hosting — Cloudflare Workers (not Pages)

**Decision:** Deploy via `@opennextjs/cloudflare` to Cloudflare Workers.
**Rationale:** CLAUDE.md explicitly states Cloudflare's current guidance — Pages now serves static exports only. Workers + OpenNext supports full SSR, RSC, and Server Actions.

**Key config requirements (from OpenNext research):**
- `compatibility_flags = ["nodejs_compat"]` — enables polyfilled Node.js APIs
- `compatibility_date = "2025-05-05"` or later
- Next.js 16+ uses Turbopack by default — OpenNext does NOT support it yet; use `--webpack` flag or pin to Next.js 15
- Worker size limit: 3MB compressed (free tier), 10MB (paid)

### ADR-02: Single-branch scope for v0.1

**Decision:** Both branches exist in the `branches` table (for display/contact), but stock is pooled (single `stock_quantity` on `products`).
**Rationale:** ROADMAP.md Phase 0 resolves this: "single-branch scope (single `branches` row, no multi-branch logic)". However, the prototype and PRD show two branches (Industrial Area + Westlands).
**Compromise for v0.1:** Both branches seeded for contact/display pages; no per-branch stock tracking; staff have no branch assignment enforced; orders/bookings route to customer-selected branch. When the two-branch rollout begins, add per-branch stock tables and migrate.

### ADR-03: Role enforcement — RLS is the source of truth, JWT claims are UX-only

**Decision:** Database RLS policies read staff role via `private.current_staff_role()` security-definer function. JWT `app_metadata.staff_role` claim is used ONLY for UI gating, never as the sole auth gate.
**Rationale:** CODE_STANDARDS.md §6 — role changes take effect immediately via database lookup, no JWT-staleness window. Cost price/margin data is restricted at the column level.

### ADR-04: Computed values as generated columns

**Decision:** Margin (`sell_price - cost_price`), order item totals, and booking totals are Postgres generated columns.
**Rationale:** CODE_STANDARDS.md §4.5 — computed values are generated columns, not application-side arithmetic.

### ADR-05: Fixed value sets as Postgres enums + check constraints

**Decision:** `staff_role`, `product_status`, `order_status`, `booking_status`, `payment_method`, `fulfillment_type`, `price_type`, `category_type` are all Postgres enums.
**Rationale:** CODE_STANDARDS.md §4.6 — fixed value sets are enums or check constraints, not free-text.

### ADR-06: Font choice — Plus Jakarta Sans (from prototype)

**Decision:** Use `Plus Jakarta Sans` (loaded via `next/font`) for v0.1.
**Rationale:** The prototype uses it throughout. DESIGN.md §3 calls for a "distinctive display face" for headings, but the client has not provided one; Plus Jakarta Sans is a solid, professional choice that matches the prototype. A distinctive display font can be swapped in later via the token system without code changes.

### ADR-07: Package manager — pnpm 9

**Decision:** pnpm 9.
**Rationale:** TECH_STACK.md §4 recommends pnpm for speed and disk efficiency. Available in environment (v9.0.0).

## 6. Auth & Role Structure

### 6.1 Supabase Auth setup

- Customer signups: standard email/password (or OAuth in future)
- Staff login: staff users are created in `staff_users` table with a reference to `auth.users`
- Custom access token hook (`supabase/functions/validate_staff_token/`) projects `staff_users.role` into JWT `app_metadata.staff_role`

### 6.2 Access token hook (Edge Function)

```ts
// supabase/functions/validate_staff_token/index.ts
import { serve } from "https://deno.land/x/supabase@/functions/src/serve.ts";
import { createClient } from "https://esm.sh/@supabase/supabase-js@2";

serve(async (req) => {
  const token = await req.json();
  const supabase = createClient(
    Deno.env.get("SUPABASE_URL")!,
    Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")!,
  );

  const { data: staff, error } = await supabase
    .from("staff_users")
    .select("role, is_active")
    .eq("id", token.user_id)
    .single();

  if (error || !staff || !staff.is_active) {
    return new Response(JSON.stringify({}), { status: 200 });
  }

  return new Response(JSON.stringify({
    app_metadata: { staff_role: staff.role }
  }), { status: 200 });
});
```

## 7. RLS Policies

### 7.1 Grant strategy

Every migration starts with:
```sql
-- Revoke default blanket grants
revoke all on schema public from public;
revoke all on all tables in schema public from public;
revoke all on all routines in schema public from public;

-- Grant to Supabase roles
grant usage on schema public to anon, authenticated;
grant select on all tables in schema public to anon;  -- public catalog only
grant select, insert, update, delete on all tables in schema public to authenticated;
```

Then per-table column-level grants and row-level policies are applied.

### 7.2 Policy matrix (per table)

#### `branches`
- **anon/authenticated**: `select` all — for contact pages
- **admin/manager/cashier**: full CRUD
- **customer**: select only

#### `categories`
- **all roles**: `select` all — needed for navigation
- **admin/manager**: insert/update/delete
- **anon**: select only

#### `products`
- **anon/authenticated/customer/cashier**: select on public columns only (name, slug, description, category_id, brand, size_spec, sell_price, stock_quantity, image_url, status, is_active). **No access to `cost_price`, `margin`**.
- **admin/manager**: full access including cost columns
- **cashier**: select on cost columns is **denied** — cost data blocked at the column level
- **insert/update**: admin/manager only

Column-level grant to enforce cost-price isolation:
```sql
-- Grant only public columns to authenticated
grant select (id, sku, name, slug, description, category_id, brand,
  size_spec, sell_price, stock_quantity, image_url, status, is_active, created_at, margin)
  on products to authenticated;
-- cost_price is NOT granted to authenticated

-- Re-grant cost_price to admin/manager via the RPC
```

#### `services`
- **all**: select all
- **admin/manager**: full CRUD

#### `orders`
- **customer**: select/insert own only (`customer_id = auth.uid()`)
- **admin/manager/cashier**: select all, update status
- **customer**: cannot change status or other customers' orders

#### `order_items`
- **customer**: select own orders' items only (via join to orders)
- **admin/manager/cashier**: full access
- **customer**: `unit_cost`, `total_cost`, `margin` columns denied

#### `service_bookings`
- **customer**: full own (create, read, update own)
- **admin/manager/cashier**: read all, update status
- **customer**: cannot update status (only their own notes)

#### `reviews`
- **anon**: select all
- **customer**: insert own, update/delete own
- **admin/manager**: select all (for moderation in future)

#### `wishlists` + `wishlist_items`
- **customer**: full own only
- **anon**: no access

#### `staff_users`
- **admin**: full CRUD
- **manager**: select only (cannot change roles)
- **cashier/customer/anon**: no access

#### `customer_profiles`
- **customer**: read/update own only
- **admin/manager**: read all
- **cashier**: read all (for in-person lookup)
- **anon**: no access

#### `vehicle` (reference data)

## 10. Edge Functions

### 10.1 Functions to implement (v0.1)

| Function | Purpose | Auth |
|---|---|---|
| `validate_staff_token` | Projects staff role into JWT app_metadata | Service role |
| `deduct_stock_on_sale` | Decrements `stock_quantity` on order confirmation | Service role |
| `calculate_margin` | Returns cost/sell/margin for a product (staff only) | Auth user |
| `process_order_status` | Handles order status transitions (admin/manager/cashier) | Staff role |
| `mpesa_webhook` | Receives M-Pesa STK/Lipa confirmation (stubbed) | Public webhook |
| `send_whatsapp_notification` | Sends order/booking status via WhatsApp (stubbed) | Service role |

### 10.2 Business logic summary

- **Stock deduction**: On `order.status` → `'confirmed'`, decrement `products.stock_quantity` by `order_items.quantity` for each item. Update product `status` to `'low_stock'` if quantity < 10, `'out_of_stock'` if 0.
- **Margin calculation**: Already a generated column on `products` and `order_items`, so this function is mainly for the POS display API.
- **Order status transitions**: draft → pending → confirmed → packed → shipped → delivered (or cancelled/refunded at any point). Only admin/manager can skip steps; cashier follows linear flow.
- **Booking status**: scheduled → confirmed → in_progress → completed (or cancelled/no_show). Cashier updates status at counter.

## 17. Execution Approaches

> Simon should pick one approach before execution begins.

### Approach A: Solo Sequential Agent (Conservative)

Single agent executes the checklist items in order, one phase at a time, with verification gates between each:

```
Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6
```

**Pros:** Linear, easy to track, low coordination overhead
**Cons:** Slower overall, no parallelism
**Timeline:** ~16-20 days

### Approach B: Parallel Tracks (Balanced)

Two parallel workstreams:

- **Backend track** (1 agent): Bootstrap + schema + auth + RLS + pgTAP + seed + Edge Functions
- **Frontend infrastructure track** (1 agent): Design system + ui primitives + config + CI/CD

After both tracks converge, a single agent does frontend wiring (routes, data fetching, checkout/booking flows).

**Pros:** Faster, leverages parallelism, design system ready when frontend connects to backend
**Cons:** Requires coordination at the integration point
**Timeline:** ~10-12 days

### Approach C: Feature-First Full-Stack (Aggressive)

Complete each customer-facing feature end-to-end before starting the next:

1. Storefront core (catalog + detail + cart + checkout) — full stack
2. Service booking — full stack
3. Staff POS + dashboard — full stack

Backend infrastructure (schema, auth, RLS) is built as needed per feature, but the full schema is laid out upfront.

**Pros:** Fast to first working demo, user-visible value early
**Cons:** Higher risk of re-architecting as features compound; RLS verification delayed until later
**Timeline:** ~12-14 days

### Approach D: TDD-First (Quality-Focused)

Write all tests first (pgTAP, Vitest, Playwright), then implement to green:

1. pgTAP tests for all tables + all roles → schema + RLS
2. Vitest tests for utilities → cn(), Zod schemas, helpers
3. Playwright tests for checkout + booking → frontend implementation

**Pros:** Highest quality, tests drive design, verification built in
**Cons:** Slowest start, may block on test design before implementation
**Timeline:** ~14-18 days
